Unit: `.text 0x161940-0x1622b0` in `d_basesNP` (0x970 bytes, 16 functions).
Class name chosen: `daWmDancePakkun_c : public dWmDemoActor_c` (see "Base class"

All evidence below that is stated as **measured** was checked with the actual
`mwcceppc.exe` compiler via `tools/auto_decomp/harness.py`'s `compile_draft()`,
using `STATIC_ASSERT`/`offsetof` probes against the real, already-landed headers

## Base class: dWmDemoActor_c, not dWmObjActor_c or dWmEnemy_c

The ctor (`fn_2_161970`) opens with `bl __ct__14dWmDemoActor_cFv` as its first
call -- that mangled name is exactly `dWmDemoActor_c` (14 chars). This alone
doesn't distinguish "extends dWmDemoActor_c directly" from "extends
dWmObjActor_c or dWmEnemy_c, whose own ctors are trivial-inline and would
inline straight through to the same `bl`" (both `dWmObjActor_c::dWmObjActor_c()`
and `dWmEnemy_c::dWmEnemy_c()` are defined in-class-body, and `-inline noauto`
still inlines in-class-body members per AGENT_CONTEXT.md).

What settles it: **measured** `sizeof(dWmDemoActor_c) == 0x184` and
`sizeof(dWmObjActor_c) == 0x188` (STATIC_ASSERT, compiled clean). The ctor's
first field write after the base-ctor call is `stw r0, 0x184(r29)` with r0=-1
-- i.e. a field starting AT byte 0x184, which is exactly where
`dWmDemoActor_c` ends. If this class went through `dWmObjActor_c`
(`mResNodeIdx` at 0x184..0x188, confirmed by a second measured probe:
`offsetof(daWmGhost_c, mUnk188) == 0x188`), the class's own fields would start
at 0x188, not 0x184. If it went through `dWmEnemy_c` (measured
`sizeof(dWmEnemy_c) > 0x184`, and by inspection dWmEnemy_c's own first member
`dWmEnPath_c mPath` is a large sub-object, not a single `int`), the ctor would
show a large sequence of sub-object construction, not one bare `-1` store
immediately followed by `dHeapAllocator_c`'s ctor 8 bytes later.

**Confidence: high.** This is the single biggest structural claim in this
report and it rests on compiled, checkable numbers, not inference from the
class's apparent behaviour.

## Open questions (not resolved -- reporting rather than guessing)

### 1. The `this+0x60` double-indirect call in the ctor and `execute()`

The ctor (`fn_2_161970`) stores the address of an anonymous 0x120-byte `.data`
object (`lbl_2_data_44648`) into `this+0x60`:
```
lis r4, lbl_2_data_44648@ha
li r0, -0x1
addi r4, r4, lbl_2_data_44648@l
stw r0, 0x184(r29)
addi r3, r29, 0x18c
stw r4, 0x60(r29)          ; this+0x60 = &lbl_2_data_44648
bl __ct__16dHeapAllocator_cFv
```
`execute()` (`fn_2_161c20`) later does:
```
lwz r12, 0x60(r30)         ; r12 = *(this+0x60)   == &lbl_2_data_44648
mr r4, r3                  ; r4 = GetCutName() result
mr r3, r30                 ; r3 = this
lbz r5, 0x164(r31)         ; r5 = dCsSeqMng_c::ms_instance->m_164 (matches ghost)
lwz r12, 0x60(r12)         ; r12 = *(lbl_2_data_44648 + 0x60)   (a function ptr)
mtctr r12
bctrl                      ; call(this, cutName, isFirstFrame)
```
This is a plausible mechanism for `processCutsceneCommand(cutsceneCommandId,
isFirstFrame)` (same two args ghost/dokan pass), but it is **not** an ordinary
C++ virtual call (that would be `lwz r12,0(r3)` then one slot lookup, not
`this+0x60` then a second `+0x60`). I measured, via `offsetof` probes against
the real (already-landed, fixed) headers, that `0x60` is **not** any named
field of `dBase_c` (`mpKindString`=0x68, `mpNameString`=0x6c) or
`dBaseActor_c` (first public field `mMatrix`=0x7c) -- so it must belong to
`fBase_c` itself (its own fields, `fManager_c mMng`, or its multiply-inherited
`cOwnerSetMg_c` sub-object; I did not have visibility into `fManager_c`'s own
layout) or `cOwnerSetMg_c` (measured non-polymorphic, so it cannot be a
secondary vtable pointer).

**I could not identify what field this is or what C++ source statement would
produce a raw store of a `.data` table address into it.** I did not invent a
new field on `dBase_c`/`fBase_c` to explain it, since those headers are
depended on by every other landed unit and inventing a field there is exactly
the kind of "big claim" this project's rules say not to apply without
explicit evidence. **What would settle it:** either (a) grep the compiled,
already-landed corpus (`bin/compiled/d_basesNP` or wherever the equivalent
lives) for another function that does `lwz r12,0x60(rX)` twice in a row on a
`dBase_c`-derived `this`, per the "read a function that already matches"
technique, or (b) ask whether `fManager_c` (declared in `f_manager.hpp`,
which I did not open) has a public/protected function-pointer-table field at
its own `+0x60`.

Because of this, **I did not attempt to author the ctor or `execute()`** --
writing `processCutsceneCommand(...)` as a normal `virtual` override would
compile to an ordinary vtable call, which I would expect NOT to match this
shape, and I did not want to submit an unverified guess as source.

### 2. Exact vtable slot for `draw()`'s `mModel.entry()`-shaped call

`draw()` (`fn_2_161d40`) is a single 0-argument virtual call through
`mModel`'s own vtable (`lwzu r12,0x1ac(r3)` then `lwz r12,0x14(r12)`, i.e.
vtable+0x14). I worked out a slot layout for `m3d::mdl_c`'s vtable by hand
from `scn_leaf.hpp`/`bmdl.hpp`/`mdl.hpp`'s declared virtuals (dtor takes 2
slots, `getType`, `remove`, `entry` inherited from `scnLeaf_c`, then
`setAnm`/`play` added by `bmdl_c`) and got `entry` at `+0x10`, not `+0x14` --
i.e. my hand-derived slot count is off by one somewhere and I do not trust it
enough to state which of `entry()`/`play()` is correct. This is exactly the
kind of thing AGENT_CONTEXT.md says to let the compiler decide rather than
argue from disassembly: compiling `draw() { mModel.entry(); return
SUCCEEDED; }` and `draw() { mModel.play(); return SUCCEEDED; }` and comparing
the emitted vtable offset against `0x14` would settle it in one compile. I
did not run that compile in this session.

### `this+0x60`, resolved by enumeration (not fixed, but now precisely bounded)

Per-member `S<offsetof(...)>` probes against `dBaseActor_c` (one member per
line, class scope, errors read in source order -- all monotonically
increasing, so no reordering artifact):

```
mUniqueID=0x0  mParam=0x4  mProfName=0x8  mLifecycleState=0xA
mDeleteRequested=0xB  mDeferExecute=0xC  mDeferRetryCreate=0xD
mGroupType=0xE  mProcControl=0xF  mMng=0x10  mpUnusedHelper=0x50
mUnusedList=0x54  mHeap=0x5C (ends 0x60)  mpKindString=0x68  mpNameString=0x6C
sizeof(fBase_c)=0x64  sizeof(dBase_c)=0x70  sizeof(dBaseActor_c)=0x128
```

`mHeap` (the last named `fBase_c` field) ends exactly at `0x60`, and
`sizeof(fBase_c)` measures `0x64` -- four bytes of *unclaimed* trailing space
inside `fBase_c` alone, before `dBase_c`'s secondary base or its own fields
even enter the picture. To rule out `cOwnerSetMg_c` (the secondary base)
occupying that gap via tail-padding reuse, I compiled the upcast itself and
read the generated adjustment off the disassembly:

```cpp
cOwnerSetMg_c *getBase(dBase_c *d) { return d; }
```
compiles to `addi r3, r3, 0x64` -- i.e. **`cOwnerSetMg_c`'s sub-object starts
at `dBase_c+0x64`, not `+0x60`.** (`getBase2` returning `fBase_c*` from the
same `d` emits no adjustment at all, confirming `fBase_c` is the primary
base at offset 0, as assumed.) `sizeof(cOwnerSetMg_c)` measures `0x4` (just
its one pointer member, no padding of its own), which is consistent with
`dBase_c`'s measured total of `0x70` = `0x64 (fBase_c) + 0x4 (cOwnerSetMg_c)
+ 0x4 (mpKindString) + 0x4 (mpNameString)`.

**Conclusion: offset `0x60` is not any named member of `fBase_c`, `dBase_c`,
`cOwnerSetMg_c`, or `dBaseActor_c` in the headers as they stand today.** It
sits inside `fBase_c`'s own reported `sizeof`, past every field the header
declares, with no alignment reason I can find for the padding to exist at
all (`0x60` is already 4-aligned; nothing in the class needs 8-alignment).
Two readings are consistent with the evidence and I can't distinguish them
further without either the original source or a landed sibling that does the
same `this+0x60` access:

- `fBase_c` is genuinely missing a field there (a real gap in an

### `+0x60`, fully resolved via corpus search (instruction 4)

Disassembled all 177 `.o` files in `bin/compiled/` (every landed unit across
all four modules, plus the DOL) and grepped for `0x60(r`. The answer was
sitting in the corpus the whole time:

- `d_base.o` (`dBase_c::dBase_c()`, landed, byte-exact): right after
  `bl __ct__7fBase_cFv`, it does `stw r0,0x64(r31)` (zeroing
  `cOwnerSetMg_c::mpRoot`) then `stw r4,0x60(r31)` where r4 was just computed
  as `lis r4,__vt__7dBase_c@ha; addi r4,r4,__vt__7dBase_c@l`. Then
  `lwz r12,0x60(r31); lwz r12,0x4c(r12); bctrl` -- a virtual call through
  THAT pointer -- whose result gets stored into `mpKindString` (`0x68`).
  That's `this->getKindString()`, called through a SECOND vtable at `+0x60`,
  not the primary one at `+0x0`.
- `d_wm_demo_actor.o` (`dWmDemoActor_c::dWmDemoActor_c()`, landed): the exact
  same shape, `stw r4,0x60(r31)` with r4 = `&__vt__14dWmDemoActor_c`,
  positioned right between the `bl __ct__10dWmActor_cFv` base-ctor call and
  constructing `mHeapAllocator`/`mModel`.
- `d_a_wm_ghost.o` (`daWmGhost_c::daWmGhost_c()` AND `::execute()`, landed,
  byte-exact): ctor does `stw r4,0x60(r29)` with r4 = `&__vt__11daWmGhost_c`,
  in the exact same position dWmDancePakkun's does (right after the
  dWmObjActor_c-inlined-through-to-dWmDemoActor_c base call, right before
  `mAllocator`'s ctor). `execute()` does the literal double-dereference --
  `lwz r12,0x60(r30); ...; lwz r12,0x60(r12); bctrl` -- to call
  `processCutsceneCommand(GetCutName(), m_164)`, the exact source line
  ghost.cpp already has.

**Conclusion: `this+0x60` is an ordinary secondary vtable pointer that every
polymorphic `dBase_c`-derived class in the game sets in its own constructor,
via completely ordinary C++ (no manual code, no header change).** Our ctor
now has an EMPTY body (`daWmDancePakkun_c::daWmDancePakkun_c() : m_184(-1)
{}`) and the compiler emits the vtable store automatically; `execute()` now
calls `processCutsceneCommand(...)` as an ordinary (uninherited-override)
virtual call. Residual on the ctor dropped from 46 differing to **4**.

The remaining 4-instruction ctor residual is a pure register-choice/ordering
swap (target stores `m_184=-1` before the vtable pointer; my draft's
compiler does it in the other order, using r3 where the target uses r4).
Tried moving `m_184=-1` from the initialiser list into the body, which made
it worse (back to 46 differing), so reverted. This reads as the
"declaration order does not drive MWCC's saved-register assignment" class of
residual AGENT_CONTEXT.md already documents as usually not source-addressable;
did not find a further lever for it this round.

I did NOT determine what `cOwnerSetMg_c` (or whatever the true secondary
