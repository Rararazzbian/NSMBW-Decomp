`.text 0x167120-0x16793c`, 12 functions + one `.ctors`-registered function
(`fn_2_1678F0`), module `d_basesNP`. Base class `dBaseActor_c` (direct,
confirmed from both the ctor's `bl __ct__12dBaseActor_cFv` and the dtor's
`bl __dt__12dBaseActor_cFv`).

## Class layout -- measured and compiler-verified

Confirmed by a `STATIC_ASSERT`/`Probe<N>`-style compile (`wip/wm_units/agent_item/probe.cpp`)
against the REAL headers already in `include/`, cross-checked instruction-by-
instruction against the ctor's explicit field-zeroing stores:

```cpp
class daWmItem_c : public dBaseActor_c {   // sizeof == 0x210, matches `li r3,0x210`
    dHeapAllocator_c mAllocator;            // @0x128
    m3d::mdl_c mModel;                      // @0x144
    m3d::anmChr_c mAnmChr;                  // @0x184, measured sizeof 0x38
    nw4r::g3d::ResFile mResFile;            // @0x1bc, main archive
    nw4r::g3d::ResFile mAnimResFile;        // @0x1c0, animation archive
    nw4r::g3d::ResAnmTexPat mResAnmTexPat;  // @0x1c4, transient, createModel() only
    m3d::anmTexPat_c mAnmTexPat;            // @0x1c8, measured sizeof 0x2c
    float mMotion[3];                       // @0x1f4
    int m_200, m_204;                       // @0x200/0x204 -- signed (target uses cmpw not cmplw)
    u8 m_208, m_209, m_20a, m_20b;          // @0x208-0x20b, state flags
    int mItemType;                          // @0x20c, mParam & 0xF -- signed (cmpwi not cmplwi)
};
```

This is the strongest-grounded layout of any unit this session: every
offset was independently confirmed two ways -- the `Probe<N>` compile error
text (`illegal use of incomplete struct/union/class 'Probe<444>'` etc, read
as decimal) AND the raw store addresses in `fn_2_167150`'s disassembly.
`mAnmTexPat`'s embedded `banm_c::mAllocator` sub-object ctor call
(`bl __ct__12mAllocator_cFv`, `r3 = this+0x1d4`) independently confirms
`mAnmTexPat` starts at `0x1c8` and that `EGG::Allocator` (via `mAllocator_c`)
is 0x1c bytes, not the 4 a naive "just a vtable pointer" guess would give --
this is what makes `sizeof(anmTexPat_c) == 0x2c`, not 0x14.

`this+0x60` is the usual auto-populated "secondary vtable" pointer (see prior
units' notes) -- no manual field or code needed for it.

## Data layout -- measured from real relocations, not guessed

`g_profile_WM_ITEM` (`.data 0x45030`, size 0xc, standard `fActorProfile_c`)
has its `classInit` field's relocation resolving directly to `fn_2_167120`
(`.text 0x167120`) -- proven with `tools/relfile.py` against
`original/d_basesNP.rel`'s own self-relocation stream (module index 2), not
inferred. This is why `.data` is claimed starting at the profile despite
`check_bounds.py`'s "wm unit opens on sc_ForceList" heuristic flagging it --
that heuristic is a *default*, not a universal rule, and here it is directly
overridden by the classInit self-relocation. `d_a_wm_kinoko_base.cpp`
(landed sibling, `WM_KINOKO_BASE`) and `WM_ISLAND` (immediately preceding
unit in `.data`, ending exactly at `0x45030` with no gap) were both read for
precedent.

Everything from `.data 0x45030` through `0x45230` (`lbl_2_data_451B8`, the
secondary vtable, ending exactly there) belongs to this unit -- confirmed by
scanning every `.text`-sourced relocation in `[0x167120, 0x16793c)` and
finding none past `0x451b8`. `.data 0x45230-0x45270` (two small objects plus
two 5-byte strings, `WM_KILLER`'s own `sc_ForceList`-shaped opener) is
**not** referenced by this unit and is excluded from the claim.

The tables following the profile (all pointer arrays of 7 entries, one per
item type 0-6, index 5 always repeating index 0's entry -- 5 real distinct
item types plus one alias):

are two adjacent `dtk`-split symbols that the target's own code treats as
ONE 12-float table -- `create()`'s item-type-5 branch reads
`lbl_2_rodata_8988+0x1c`, past the first object's declared 0x18-byte size,
through the SAME base register used for the first 6. Values (read directly
from `original/d_basesNP.rel` .rodata, file offset `0x1c6600+addr`):
`{-32, 200, 3.2, 0.65, 0, 1000, 1.0, 0.65, 2.0, 3.2, -32, 200}`.

`lbl_2_data_4503C` (0x14 bytes) is patched at load by the guarded `.ctors`
function (`fn_2_1678F0`, castle/dance_pakkun-shaped: `s8` guard at
`lbl_2_bss_FDF8`, `extsb.`/`bnelr` test) with the first 4 floats of the
table above. The trailing 4 bytes (offset 0x10) are never referenced by any
of this unit's 12 functions.

## Negatives (every one measured, not guessed)

1. **`create()`/`step0`/`step1`/`step2` are never called from any of this
   unit's other 11 functions.** They must be reached through some
   polymorphic mechanism outside this unit's own code (likely the
   "secondary vtable" at `this+0x60`, auto-populated by the compiler for
   some base interface this class implements alongside `dBaseActor_c`).
   `create()`'s exact signature is itself uncertain: the target never sets
   `r3` before returning (no `li r3,SUCCEEDED`), which is why `virtual int
   create()` returning `SUCCEEDED` is a guess, not a measurement -- `mwcc`
   rejects a `void create()` override of `fBase_c::create()` (error 10227),
   so *some* int-returning shape is required, but the real return value is
   unconfirmed.

2. **`createModel()`, `calcModel()`, and `cycleAnm()` all show the same
   residual defect class**: the target caches `lbl_2_rodata_8988`'s (or
   `lbl_2_rodata_89A0`'s) base address in one dedicated register for the
   whole function (e.g. `calcModel()`'s `r31`), while the isolated draft
   recomputes the constant-table address at each access site, costing one
   extra `lis`/`addi` pair per site and cascading a register-allocation
   shape mismatch through the rest of the function. Introducing a local
   `const float *k = sConstTable;` alias measurably helped `calcModel()`
   (68 -> 60 differing) but did not fully resolve it. This is the same open
   problem `dance_pakkun`'s `createModel()` hit with its own play-mode
   table and was never fully solved there either -- it looks like a
   systemic pattern for this project's isolated-compile register allocator,
   not a one-off bug in this unit.

3. **`fn_2_167750` (`cycleAnm`) is otherwise exact**: every one of its 17
   `difftool.py`-reported differences is either (a) the same rodata-caching
   issue as above (one extra instruction, cascading the rest), or (b) a
   symbol-name text difference (`lbl_2_data_451B0` vs the local
   `sCycleAnmNames`) that will resolve once linked against the real
   addresses. No logic differs.

4. **`fn_2_1678F0` (`.ctors` init) is fully structurally exact.** Every one
   of the 12 `difftool.py`-reported differences is symbol-name text
   (`lbl_2_bss_FDF8`/`lbl_2_rodata_8988`/`lbl_2_data_4503C` vs this
   isolated compile's own anonymous-namespace object names) or an offset
   difference caused by the merged 12-float `sConstTable` sitting at a
   different position relative to *this function's own* anonymous pool than
   the real target's `lbl_2_rodata_8988` sits relative to *its* neighbours
   -- not a content or ordering defect.

5. **Fixed two real bugs found only by measuring, not by design intuition**:
   `mItemType`/`m_200`/`m_204` must be `int`, not `u32` -- the target
   compares them with `cmpwi`/`cmpw` (signed), and using unsigned types
   produced `cmplwi`/`cmplw` instead, a real byte-level defect on `create()`
   and (partially) `cycleAnm()`. And chained assignment (`mScale.x =
   mScale.y = mScale.z = v;`) store order is `z,y,x` (right-to-left, per
   C++ assignment-operator chaining semantics) while the target stores
   `x,y,z` in declaration order -- fixed by writing three separate
   statements everywhere a vec3 gets a uniform value.

6. **Do not call the base destructor explicitly.** An initial
   `daWmItem_c::~daWmItem_c() { dBaseActor_c::~dBaseActor_c(); }` compiled
   to a *double* `bl __dt__12dBaseActor_cFv` (one from the manual call, one
   auto-generated) plus an unwanted manual secondary-vtable-pointer reset
   at `this+0x60` that the target's dtor never performs. An empty `{}` body
   (letting the compiler auto-generate the destruction chain) is the fix --
   same "do not initialise/destroy what the compiler already handles" rule
   as manta's ctor negative, now confirmed for destructors too.

7. **`mAnmTexPat.mpChildren`, not a separate field, occupies `this+0x1f0`.**
   An earlier layout draft declared a spurious extra `u32 m_1f0;` member
   between `mAnmTexPat` and `mMotion`, based on a naive reading of the
   ctor's zero-stores before the `Probe`-verified `sizeof(anmTexPat_c) ==
   0x2c` was known. Removed once the real size made clear the ctor's
   `stw r31, 0x1f0(r29)` is `anmTexPat_c`'s own last field
   (`mpChildren`), not a class member of `daWmItem_c` -- this was caught
   before it reached the header, but is recorded since it is exactly the
   kind of same-size-different-owner mistake `check_bounds.py`'s docstring
   warns about, just one level down (struct field, not `.data` symbol).

## Tools used beyond the standard set

`tools/relfile.py`'s `Rel` class was loaded directly (not through any
existing wm_units script) to walk `original/d_basesNP.rel`'s own
self-relocation stream (module index == the REL's own index, confirmed 2)
and answer two questions no amount of disassembly reading alone can settle
with certainty: (a) exactly which `.data` addresses are *pointed to* by the
anonymous pointer tables following the profile (their targets never appear
as `.text`-sourced relocations, since they're reached via pointer
arithmetic off the already-relocated profile address, not per-entry
relocations), and (b) exactly which `.data`/`.rodata`/`.ctors` addresses
are referenced *from* this unit's own `.text`/`.ctors` ranges, which is what
let `.data`'s upper bound (`0x45230`, not `0x45270`) be settled with
certainty rather than guessed from the `check_bounds.py` heuristic alone.
Scratch scripts: `dump_relocs.py`, `dump_text_refs.py`, `dump_ctors.py`,
`dump_strings.py`, `dump_prefix.py`, `dump_more.py` (all in this directory).
`probe.cpp`/`probe_build.py` hold the layout-verification compile.
